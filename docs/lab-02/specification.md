# Lab 2 Sprint Engineering Specification

## 1. Sprint Goal

Deliver a working Requester-facing ticketing experience for TokTickIT. By the end of this sprint, an authenticated-by-selection Requester can create IT support tickets, upload permitted attachments, view and search their own ticket list, open a Ticket Detail screen, and add or soft-remove attachments — all within a consistent Zen Green UI. A temporary Development Requester selector replaces real login for this sprint.

---

## 2. Stakeholder Request Interpretation

The IT department needs a professional Requester-facing portal. Requesters must be able to describe a problem, classify it, indicate priority, attach evidence, and submit a ticket. After submission, they must be able to find their tickets in a searchable, filterable, paginated list, open a Ticket Detail screen, and manage permitted attachments. The system must generate an official Ticket Number, store data safely, and prevent cross-Requester data access. Because real authentication arrives in Lab 3, a temporary Development Requester Selection screen is used as a testing mechanism. A consistent Zen Green visual theme and reusable components must be established now for future reuse.

---

## 3. Scope

### Included

- Development Requester Selection screen (temporary testing mechanism, not real login)
- Application shell with navigation: My Tickets, Create Ticket, current Requester display, Change Requester
- Create Ticket screen (form, validation, submission, success, failure states)
- My Tickets screen (paginated list, search, filter, sort, loading/empty/no-results/failure states)
- Requester Ticket Detail screen (read-only ticket information + attachment management)
- Attachment lifecycle: upload, preview (active), download (active), soft removal with reason
- Ownership protection: a Requester may not view or access another Requester's tickets or attachments
- Zen Green Theme UI tokens and reusable components (form, list, badge, loading, empty, error, responsive layout)
- PostgreSQL data model: DevRequester, Ticket, Attachment, Category, RelatedSystem
- REST API for all required capabilities
- Seed data: 4 Categories, 6+ Related Systems, 4+ active DevRequesters, 1+ inactive DevRequester
- Automated tests: unit, API, UI component, UI style, responsive, and E2E

### Excluded

- Real authentication: login, logout, passwords, sessions, tokens, role-based authorization
- IT Staff workflow: staff dashboard, queue, claiming, reassigning, changing IT Priority
- Ticket collaboration: Public Comments, Internal Notes, Actions Taken
- Ticket lifecycle changes beyond initial New status (resolving, closing, reopening, cancelling)
- Administration functions: user/role/reference-data management

## 4. Functional Requirements

- **FR-01** The system provides a Development Requester Selection screen that loads active Requesters from the database. The Requester selects one and clicks Continue. The selected identity is stored in the application context and used for all subsequent operations.
- **FR-02** The application shell displays the current Requester's name and provides a Change Requester action that returns to the Selection screen.
- **FR-03** A Requester can open the Create Ticket screen, fill in required fields, and submit the form to create a new Ticket.
- **FR-04** The backend generates a unique, official Ticket Number upon successful creation.
- **FR-05** After successful submission, the Ticket Number is displayed and the Requester can navigate to My Tickets or create another ticket.
- **FR-06** A Requester can view only their own Tickets in My Tickets.
- **FR-07** My Tickets supports keyword search across Ticket Number and Summary, filtering by Category and Current Status, sorting by Created Date and Last Updated, and page-based pagination.
- **FR-08** A Requester can open a Ticket Detail screen for any of their own Tickets.
- **FR-09** The Ticket Detail screen is read-only for ticket header fields. No status changes, comments, or IT Staff actions are available.
- **FR-10** A Requester can add a permitted attachment to an existing Ticket (provided the active-attachment limit is not reached).
- **FR-11** A Requester can download an active attachment from a Ticket they own.
- **FR-12** A Requester can soft-remove one of their own active attachments by providing a removal reason.
- **FR-13** Soft-removed attachments remain visible as metadata (filename, removed timestamp, removal reason) but cannot be downloaded or previewed.
- **FR-14** The system shows appropriate loading, empty, no-results, and failure states on all screens.
- **FR-15** All screens must be responsive across desktop (992 px+), tablet (768-991 px), and mobile (under 768 px) viewports.

## 5. Business Rules

- **BR-01** The official Ticket Number is generated by the backend and must be unique across all Tickets. Format: `TK-YYYYMMDD-NNNN` where NNNN is a zero-padded sequential counter per day.
- **BR-02** A new Ticket begins with Current Status `NEW`.
- **BR-03** Lab 2 uses a Development Requester selector instead of real login. The selected identity is for testing only and is not authentication. It must be clearly labeled as such in the UI.
- **BR-04** Only active Requesters appear in the Development Requester dropdown. Inactive Requesters must be excluded.
- **BR-05** After selecting a Requester, all ticket-related operations are scoped to that Requester's identity. Switching Requester reloads all Requester-specific data.
- **BR-06** A Requester may only view, access, or modify their own Tickets and Attachments. Any attempt to access another Requester's resources must return an ownership-failure response (403 or 404).
- **BR-07** Ticket Summary: required; 5-200 characters; leading/trailing whitespace trimmed before validation and storage.
- **BR-08** Ticket Description: required; 10-5000 characters; leading/trailing whitespace trimmed before validation and storage.
- **BR-09** Category: required; must be an active Category from the reference table.
- **BR-10** Related System: required; must be an active Related System from the reference table.
- **BR-11** Requested Priority: required; one of `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`.
- **BR-12** Ticket Number, Ticket Date, Current Status, and Requester are system-generated or system-assigned; they are not editable by the Requester.
- **BR-13** The Create Ticket form retains all user-entered values if submission fails (frontend or backend error), so the Requester does not lose their work.
- **BR-14** The Submit button enters a busy/disabled state while the request is in flight to prevent duplicate submissions.
- **BR-15** Attachment allowed types: JPG/JPEG, PNG, WEBP, PDF only.
- **BR-16** Maximum attachment size: 5 MB per file.
- **BR-17** Maximum active attachments per Ticket: 5. Uploading a sixth attachment while 5 are active must be rejected.
- **BR-18** Attachment removal is implemented as soft removal: the record is marked `isRemoved = true`, a `removedAt` timestamp and `removalReason` are stored. The file is no longer downloadable.
- **BR-19** A Requester may only remove attachments on Tickets they own.
- **BR-20** Removal requires a non-empty removal reason.
- **BR-21** If a Ticket is created successfully but an attachment upload subsequently fails, the Ticket remains saved. The attachment failure is reported without rolling back the Ticket.
- **BR-22** Filenames are sanitized before storage to prevent path traversal. Storage uses a generated unique key (UUID), not the original filename.
- **BR-23** My Tickets returns only the currently selected Requester's Tickets. Default sort: `createdAt DESC`. Secondary sort: `id DESC` to break ties.
- **BR-24** Pagination default page size: 10. Permitted page sizes: 10, 25, 50. Invalid page or size values return a 400 error.
- **BR-25** If no active Requesters exist in the database, the Selection screen shows a meaningful empty state.
- **BR-26** If the API call to load active Requesters fails, the Selection screen shows a safe failure state with a retry option.
- **BR-27** All main screens redirect to the Development Requester Selection screen if no Requester context is present.
- **BR-28** The inactive Requester must not appear in the Development Requester selector and must not be selectable.
- **BR-29** In Lab 3, the DevRequester model will be replaced by real authentication. The schema must allow the Ticket's `requesterId` foreign key to be migrated to a real User table without data loss.

## 6. UI Specification Summary

See `docs/lab-02/ui-spec.md` for the complete visual and component specification.

### Application Shell

- Persistent top navigation bar: TokTickIT logo/title, My Tickets link, Create Ticket link, current Requester name display, and Change Requester button.
- Active page is highlighted using the Zen Green accent color.
- On mobile (under 768 px), navigation collapses into a hamburger menu or simplified bottom bar.

### Development Requester Selection Screen

- Centered card with Zen Green styling.
- TokTickIT title, explanatory text: *"Select a Development Requester to test requester-specific ticket behavior. This is not a login screen. Authentication and role-based access will be introduced in Lab 3."*
- Dropdown populated with active Requesters (name + email).
- Continue button (disabled until a Requester is selected).
- Loading state while fetching Requesters; empty state if none; safe failure state with retry if API fails.

### Create Ticket Screen

- System-generated read-only fields at the top: Ticket Number (placeholder "Will be assigned"), Ticket Date, Current Status ("New"), Requester — visually distinct from editable fields.
- Editable fields: Category (select), Related System (select), Requested Priority (select), Summary (text input), Description (textarea).
- Attachments section below Description with file picker and file list.
- Primary "Submit Ticket" button and secondary "Cancel" button at the bottom.
- Field-level validation messages directly below each invalid field.
- Submit button shows busy state and is disabled while the request is in flight.
- Success state shows generated Ticket Number with "View Ticket" and "Create Another" actions.
- Failure state shows safe error message; all form values are retained.

### My Tickets Screen

- Page heading "My Tickets" with a "Create Ticket" primary button.
- Search bar (searches Ticket Number and Summary).
- Filter controls: Category filter, Status filter.
- Sort control: Created Date or Last Updated, ascending or descending.
- Desktop: results table. Mobile: card list.
- Visible fields: Ticket Number, Summary, Category, Current Status badge, Created Date, Last Updated.
- Pagination controls (previous/next, page selector).
- States: loading skeleton, empty (no tickets), no-results (search/filter returned nothing), failure (API error with retry).

### Requester Ticket Detail Screen

- Read-only ticket header: Ticket Number, Ticket Date, Requester, Category, Related System, Requested Priority, Current Status badge, Summary, Description.
- Attachments section:
  - Active attachments: filename, file type, size, upload date, Download button, Remove button.
  - Removed attachments: filename (strikethrough), removed timestamp, removal reason (no download available).
  - "Add Attachment" button (disabled when 5 active attachments are present).
  - Soft-remove opens confirmation dialog requiring a non-empty removal reason.
- Back navigation to My Tickets.

### Badges

- Current Status `NEW`: pale green background (`#EAF6EF`), primary green text (`#006B3C`).
- Requested Priority: LOW = gray, MEDIUM = blue, HIGH = amber, CRITICAL = red.

### Responsive Rules

- Desktop 992 px+: multi-column form layout; ticket list as table.
- Tablet 768-991 px: two-column where practical; table may reduce visible columns.
- Mobile under 768 px: fields stack vertically; table collapses to cards; buttons touch-friendly (min 44 px height); no horizontal page scrolling.

### Enums

```
RequestedPriority: LOW, MEDIUM, HIGH, CRITICAL
TicketStatus: NEW
```

### Relationships

- DevRequester 1 -- many Ticket
- Category 1 -- many Ticket
- RelatedSystem 1 -- many Ticket
- Ticket 1 -- many Attachment

### Indexes and Constraints

- `Ticket.ticketNumber` unique index
- `Ticket.requesterId` indexed (ownership filter)
- `Ticket.categoryId` indexed
- `Ticket.currentStatus` indexed (filter)
- `Ticket.createdAt` indexed (default sort)
- `Attachment.ticketId` indexed
- `Attachment.isRemoved` indexed (active-only filter)

### Design Decision

`TicketStatus` is an enum rather than a free-text field so that valid states are enforced at the database level. Starting with only `NEW` allows future states to be added via a Prisma migration in later labs without changing the column type or restructuring existing data.

### Seed Data

- **Related Systems (7):** Email, Campus Wi-Fi, VPN, LEB2 App, Grade Submission App, Printer, Corporate Laptop
- **Active DevRequesters (4):** Alice Tanaka (alice.tanaka@example.com), Bob Chavez (bob.chavez@example.com), Carol Meier (carol.meier@example.com), David Sorn (david.sorn@example.com)
- **Inactive DevRequester (1):** Eve Former (eve.former@example.com) — `isActive = false`

Seed is idempotent: uses `upsert` on unique fields to avoid duplicates on re-run.

### Migration Strategy

The schema is versioned using Prisma Migrate. The `requesterId` foreign key on Ticket mirrors the shape a real User table will use in Lab 3. The Lab 3 migration will update only the foreign key reference target; no column restructuring or data loss is anticipated.

## 9. Acceptance Criteria

- **AC-01** Given valid Ticket data, when the Requester submits the form, then one Ticket is saved, the backend returns 201, and the official Ticket Number is displayed on screen.
- **AC-02** Given no Development Requester has been selected, when the user navigates to My Tickets or Create Ticket, then the application redirects to the Development Requester Selection screen.
- **AC-03** Given Requester B is selected, when a request referencing a Ticket owned by Requester A is made, then the API returns 403 or 404 and the data is not returned.
- **AC-04** Given the Create Ticket form is submitted with missing or invalid fields, then field-level error messages appear near each invalid field and the API is not called.
- **AC-05** Given valid Ticket data and a rapid re-submission (double-click), then only one Ticket is created (Submit button disabled during submission).
- **AC-06** Given an attachment with an unsupported type or size exceeding 5 MB, when the Requester attaches it, then a clear error message is shown and the file is not uploaded.
- **AC-07** Given 5 active attachments on a Ticket, when the Requester attempts to add a sixth, then the Add Attachment control is disabled or shows a descriptive error.
- **AC-08** Given a Requester has Tickets, when they view My Tickets, then only their own Tickets appear.
- **AC-09** Given a search keyword, when the Requester searches My Tickets, then only Tickets with matching Ticket Number or Summary are shown.
- **AC-10** Given a Category filter is applied, then only Tickets in that Category are shown.
- **AC-11** Given sorting by Created Date descending, then the most recently created Ticket appears first.
- **AC-12** Given more Tickets than fit on one page, when the Requester clicks Next, then the next page of Tickets loads.
- **AC-13** Given no Tickets exist for the selected Requester, when My Tickets loads, then a meaningful empty state is shown.
- **AC-14** Given the API fails when loading My Tickets, then a safe failure message is shown with a retry option.
- **AC-15** Given a Requester opens a Ticket Detail they own, then all ticket header fields are read-only and the Attachment section is visible.
- **AC-16** Given a Requester successfully uploads an attachment, then it appears in the list and can be downloaded.
- **AC-17** Given a Requester soft-removes an attachment with a valid reason, then the attachment is marked removed, metadata is retained, and the download link is unavailable.
- **AC-18** Given a Requester attempts to access the download URL of a removed attachment, then the server returns 403 or 404.
- **AC-19** Given the backend is unavailable during Ticket creation, then the form shows a safe error state with all entered values preserved.
- **AC-20** Given a desktop viewport (992 px+), when any screen is viewed, then no labels are clipped, no buttons hidden, and no horizontal scrolling occurs.
- **AC-21** Given a mobile viewport (under 768 px), when any screen is viewed, then fields stack vertically, buttons are touch-friendly, and no horizontal scrolling occurs.
- **AC-22** Given an inactive Requester exists in the database, then that Requester does not appear in the Development Requester Selection dropdown.
- **AC-23** Given a Requester is selected and then switched, then My Tickets reloads and shows only the new Requester's Tickets.

## 11. Assumptions and Decisions

- **Ticket Number format:** `TK-YYYYMMDD-NNNN` (e.g., `TK-20260901-0001`). The counter resets daily and is generated atomically at the backend to prevent duplicates. Chosen for human readability and sortability.
- **File storage:** Attachments are stored on the local filesystem under a path using the UUID `storageKey`. No external object storage is required for Lab 2.
- **Pagination style:** Page-based (page number + page size) chosen over cursor-based for simplicity and compatibility with the required filter/sort combinations.
- **Change Requester behavior:** Clicking Change Requester clears the selected-Requester context and navigates to the Selection screen. If a Create Ticket form is in progress, the user is warned before context is cleared.
- **Attachment download:** Implemented as a server-proxied download endpoint (not a direct static URL) so that ownership and removal checks are enforced at the API layer before any file bytes are sent.
- **Removal reason:** Stored as a plain text string with a minimum of 1 character. No maximum character limit set at this stage.
- **Lab 3 migration path:** The `DevRequester` model will be replaced or supplemented by a real `User` model. The Ticket `requesterId` column will be re-pointed via a Prisma migration with no structural column changes anticipated.
